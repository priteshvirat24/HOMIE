You are a Principal Mobile Engineer, Computer Vision Engineer, 3D Graphics Engineer, ML Infrastructure Engineer, Backend Architect, Product Designer, and DevOps Engineer working autonomously inside an AI IDE.

Your task is to design and build a production-grade mobile application that allows users to capture guided photographs of rooms, reconstruct those rooms into navigable 3D environments using an open-source reconstruction repository, and explore the generated environment directly on a mobile phone using first-person controls.

Do not build a fake prototype.

Do not use placeholder implementations for core functionality.

Do not simulate reconstruction progress.

Do not hardcode generated rooms.

Do not claim that reconstruction works until the external repository has been inspected, installed, executed, tested, and its actual output format verified.

The application must be architected around the actual technical capabilities and limitations of the provided open-source repository.

image-blaster
Creates 3D environments, SFX, and meshes from a single image using Claude skills, World Labs, and FAL.

Can take you from an image to a fully meshed 3D environment in < 5 minutes, great for jumpstarting 3D work. Go full blast.

Quickstart
Open a Terminal, enter git clone https://github.com/neilsonnn/image-blaster
Enter the directory with cd image-blaster
Run claude (install with curl -fsSL https://claude.ai/install.sh | bash)
Say hello to Claude, and give them your API key for World Labs and FAL.
Put an image into input/ directory and ask Claude to blast it and confirm each step with me.
Description
By default image-blaster will use your input image to create:

3D models (.glb, .obj) of all dynamic objects
Gaussian splat (.spz) of the static environment,
Ambient looping sound and object specific physics SFX (.mp3)
Extensions
You can embed image-blaster under the assets of any game engine, DCC software, or web app.

Unity, Unreal, or Godot game engine
Blender, 3DS Max, or Maya or other DCC software
Three.js web app or Electron app
Advanced
IMAGE-BLASTER uses a few generation models:

marble-1.1 - World Labs Marble model creates the explorable environment.
nano-banana - default image edit preference for source cleanup, clean plates, and object reference images.
gpt-image-2 - alternate image edit provider when the edit skill is asked to prefer it.
hunyuan-3d - Hunyuan 3D model creates 3D object models through FAL.
elevenlabs-sfx - ElevenLabs sound effects model creates ambient and object-specific sounds.
3D model creation supports these Hunyuan parameters:

--face-count <40000-1500000>: target face count. IMAGE-BLASTER defaults to 50000; Hunyuan's API default is 500000.
--enable-pbr true|false: enable PBR material generation. Defaults to true.
--generate-type Normal|LowPoly|Geometry: Normal creates a textured model, LowPoly applies polygon reduction, and Geometry creates a white geometry-only model. Defaults to Normal.
--polygon-type triangle|quadrilateral: polygon type for LowPoly. Defaults to triangle.
Examples
Video game level concepts? IMAGE-BLAST it.
Your childhood bedroom? IMAGE-BLAST it.
Need an environment for a robot? IMAGE-BLAST it.
A film location scout? IMAGE-BLAST it.
An architectural rendering? IMAGE-BLAST it.

# 3. DEVELOPMENT PRINCIPLES

Follow these rules throughout implementation.

1. Inspect the existing codebase before changing anything.

2. Never blindly overwrite working architecture.

3. Document major architectural decisions.

4. Build vertically integrated features instead of generating hundreds of disconnected files.

5. After every phase:

* compile
* run linting
* run tests
* fix errors
* execute the application
* verify the feature manually
* update documentation
* commit logically separated changes if Git is available

6. Never hide errors using empty catch blocks.

7. Never disable TypeScript strict mode to solve errors.

8. Never replace real functionality with mock data unless the current phase explicitly requires a mock interface boundary.

9. Keep reconstruction technology behind an abstraction layer.

10. Do not couple the mobile application directly to Image Blaster.

11. Never execute heavy reconstruction workloads on the mobile device unless repository analysis proves that on-device execution is technically viable.

12. Store original images separately from reconstruction artifacts.

13. Treat reconstruction jobs as asynchronous, resumable jobs.

14. Make every upload resumable.

15. Make every reconstruction job retryable.

16. All long-running operations require progress reporting.

17. The app must survive termination, network loss, upload interruption, backend restart, and reconstruction worker failure.

# 9. CAPTURE STRATEGY

Design a capture strategy optimized for reconstruction quality.

Default strategy:

PASS 1: HORIZONTAL COVERAGE

Walk around the perimeter.

Capture walls and room center.

Maintain sufficient overlap.

PASS 2: LOWER COVERAGE

Capture furniture bases, floor transitions, and lower geometry.

PASS 3: UPPER COVERAGE

Capture upper walls, cabinets, ceiling transitions, and tall objects.

PASS 4: DETAIL COVERAGE

Capture regions identified as low-confidence.

The UI must display the current capture stage.

Example:

Stage 1 of 4

Horizontal Coverage

12 / 25 recommended images accepted.

The system must provide visual directional guidance.

# 37. EXECUTION RULES FOR THE AI IDE

You are not merely producing recommendations.

You must implement the system.

For every phase:

1. Inspect relevant existing code.

2. Explain the implementation plan.

3. List files that will be created or modified.

4. Implement one coherent vertical slice at a time.

5. Run dependency installation.

6. Run builds.

7. Run type checking.

8. Run linting.

9. Run tests.

10. Start required services.

11. Execute smoke tests.

12. Inspect failures.

13. Fix failures.

14. Repeat until the phase passes.

15. Update documentation.

16. Summarize what actually works.

17. State what remains unverified.

Do not dump thousands of lines of code without executing them.

Do not move to later phases while the current foundation is broken.

Do not repeatedly ask the user for permission to continue.

Proceed autonomously unless:

* credentials are required
* a destructive operation requires confirmation
* repository access is unavailable
* a product decision fundamentally changes architecture
* required hardware is unavailable

When blocked, document:

BLOCKER

CAUSE

ATTEMPTED SOLUTIONS

EXACT USER ACTION REQUIRED

NEXT STEP AFTER RESOLUTION
